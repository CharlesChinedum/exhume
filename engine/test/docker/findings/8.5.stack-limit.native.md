# 8.5 Handler stack limit without via_ir (native)
**PASS** (estimator sound on every tested signature; exact on all of them)
- forge: forge 1.5.1-stable, solc 0.8.28 for `test/**`, default profile (`optimizer = false`), no `via_ir`. Native macOS only, no Docker.
- Method: `engine/test/seance/project-generator.stack-experiment.test.ts` (runs only with `STACK_EXPERIMENT=1`). For each synthetic function `f` it generates the real handler with the skip disabled (`maxHandlerStack: Infinity`), writes the stage 1 and stage 2 files and runs `forge build --offline`. A build is a failure only when the output contains `Stack too deep`; any other error aborts the experiment (none occurred).
- The handler and test files are compiled under the default profile, which has the optimizer off. The `legacy_opt` profile only applies to files whose restriction has `min/max_optimizer_runs`, which are the legacy source (and the port source when `portSharesLegacyOptimizer` is set), never `test/**`. A run with the optimizer switched on for the default profile (not a real configuration) gave the same result for 300 signatures, as expected: the legacy code generator does not move variables, so the optimizer does not change the limit.

## Homogeneous signatures (k copies of one kind, k = 1..16)
Largest k that builds / smallest k that fails. Monotone in k for every kind (no pass after a fail).

| kind (Solidity type) | non-payable | payable |
|---|---|---|
| scalar: `uint256`, `uint16`, `bool`, `bytes32` | 9 / 10 | 8 / 9 |
| `address` | 9 / 10 | 8 / 9 |
| `bytes` | 4 / 5 | 4 / 5 |
| `string` | 4 / 5 | 4 / 5 |
| `address[]` | 3 / 4 | 2 / 3 |
| `uint16[]` | 3 / 4 | 2 / 3 |

Largest signature that builds in these runs: nine `uint256` parameters (or a mix with the same cost, such as `bytes, string, address[], uint16, uint256`). Smallest failing: ten `uint256`, or the same mix plus one more parameter. `two(bytes,string,address[],uint16[],bytes32[])` fails to build (estimate 18).

## Estimator
`estimateHandlerStack(fn) = 7 + (payable ? 1 : 0) + sum(cost)`, with cost 1 for a scalar or `address`, 2 for `bytes` or `string`, and 3 for `address[]` or any other dynamic array. Fixed part 7: return label, `pick`, `actorIdx`, `p`, `cd` and the encoder's temporaries. Array cost 3: the two external parameters (length, seed or index pack) plus the memory array local.

`MAX_HANDLER_STACK = 16`. The numbers above follow from the homogeneous table: scalars give 7 + 9 = 16, `bytes` 7 + 4 * 2 = 15 (5 * 2 gives 17), arrays 7 + 3 * 3 = 16 (4 * 3 gives 19), and payable adds 1. All costs are positive, so adding a parameter strictly increases the estimate.

This is an empirical result on kinds `uint256`, `uint16`, `address`, `bool`, `bytes32`, `bytes`, `string`, `address[]`, `uint16[]` only. Other scalar widths and `intN` behave like the scalars tested (the same `uint256` slot in the handler), but were not compiled one by one. If a signature outside this set fails, add its kind to the experiment and raise its cost.

## Skip behaviour
A function over the limit gets no `handler_<name>`, no entry in `handlerSelectors()` (Seance and Witness), no `targets_<name>()`, and its seed calls are dropped. It stays in `Targets.isKnownSelector`, so the fallback handler's unknown-selector search never picks it. Its sites are `unreachable` (`generateTargets(report, abi, skipped)`), and the generator returns `skippedFunctions: [{ name, reason: "stack" }]`. If the skip leaves no handler (no other function, no fallback), generation fails with `INVALID_INPUT`.

## Known limitation
A skipped function is never fuzzed, so a bug that only that function can reach is invisible to the séance. The report lists these functions in `skippedFunctions` (task 9.3). The limit can be raised by compiling with `via_ir`, which the design excludes (decision 19).
